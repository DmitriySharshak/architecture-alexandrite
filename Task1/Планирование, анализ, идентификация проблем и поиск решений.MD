## Анализ и идентификация проблем

Контекст:
1. Ежемесячный прирост на 100 заказов + открытие API для внешних продавцов привели к резкому увеличению нагрузки на систему;
2. Переход в облако сохранил монолитную структуру характерные для on-premise. т.е остался один инстанс на приложение, одна БД на запись/чтение.

Проблемные места:
1. Отсутствует горизонтально масштабирование, все сервисы Shop API, CRM API, MES API, а так же БД развернуты в единственном экземпляре, что создает точки отказа и 
   является узким местом для растушей нагрузки;
2. Медленная загрузка представлений в MES даже после введения фильтров и пагинации проблема указывает на то, что проблема а на уровне базы данных или бэкенда. 
   Скорее всего, SQL-запросы к PostgreSQL не оптимизированы, либо отсутствуют необходимые индексы;
3. Долгий расчет стоимости (до 30 минут). Текущая архитектура не подразумевает асинхронной обработки. Пользователь онлайн-магазина или внешней системы (API) вынужден долго ждать.
   Это основная причина недовольства клиентов и потери заказов.
4. Жалобы на заказы, которые «не получили» потенциально монут говорить о потере сообщений. Использование RabbitMQ между MES и CRM не описывает механизмов обработки ошибок, DLQ очередей
   Сбои при обработке сообщений или при записи в БД могут привести к потере событий или к несогласованности конечного статуса заказа
5. Ручной деплой замедляет доставку исправлений критических багов и увеличивает срок выдачи новыых функциональных блоков (Фич)
6. Ручное E2E тестирование требует много времени на проведение регрессионного тестирования. с ростом функциаональности время будет только возростать 
7. Отсутствие метрик по ключевым показателям производительности, реагирование на проблемы только по факту обращений клиентов  


Инициативы:
1. Модифицировать Shop API и MES API для работы через очередь. Запрос на расчет стоимости реализовать через очередь на расчет стоимости. Результаты расчета так же реализовать через очередь или вызыв callback в Shop API. 
2. для повышения эффективности работы операторов, провести анализ медленных запросов в MES, PostgreSQL. Добавить необходимые индексы.
3. Реализовать паттерн саги (хореография на базе RabbitMQ) для перехода заказа по статусам. Каждый сервис (Shop, CRM, MES) подписывается на нужные события и публикует результаты своей работы. Добавить механизмы компенсации на случай ошибок.
4. Настроить автоматический деплой в release-окружение после успешного прохождения тестов в dev
5. Внедрить практики IaC для управления инфраструктурой
6. Выделить время QA на написание автотестов. Начать с покрытия happy pass сценариев
7. Перевести MES API и Shop API в кластерный режим работы с несколькими инстансами. Настроить балансировщик нагрузки. Перевести БД на кластер master-slave

Приоритеты:
1. Наивысший приоритет (Must Have): Внедрение асинхронного расчета стоимости;
2. Высокий приоритет (Should Have): Оптимизация дашборда MES; 
3. Высокий приоритет (Should Have): Внедрение саги для управления статусами;
4. Высокий приоритет (Should Have): Автоматизация регрессионного тестирования;
5. Средний приоритет  (Could Have): Автоматизация деплоя;
6. Средний приоритет  (Could Have): Горизонтальное масштабирование.

Рассуждения:
1. Асинхронный расчет стоимости решает самую острую проблему - потерю клиентов из-за невозможности дождаться расчета. 
   Это напрямую влияет на выручку. Без этого любые другие улучшения бессмысленны, так как клиенты просто уходят.
2. Оптимизация дашбордов и автотестов - это решение проблем с внутренней операционной работой.


Целевая архитектура через полгода:
1. Расчет стоимости полностью асинхронный. Пользователь видит прогресс. Бэкенды общаются через RabbitMQ;
2. Повышена согласованность данных. Статусы заказов не зависают и находятся в актуальном состоянии;
3. Реализованы обработчики сбоев (DLQ);
4. Автоматический деплой на dev и release;
5. Дашборд оператора загружается быстро (<5 сек) за счет оптимизированных запросов и индексов;
6. Добавлен балансировщик и второй инстанс для MES API (первый шаг к масштабированию)

Выбор трех инициатив на полгода:
1. Внедрить асинхронный расчет стоимости, чтоюы престать терять клиентов и деньги;
2. Повысить производительность операторов, чтобы  ускорить скорость прохождения заказов;
3. Автоматизация регрессионного тестирования, для быстрой доставки ценности.
