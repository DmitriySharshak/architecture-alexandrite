## Мотивация

Уважаемая команда!
Мы внедряем распределенный трейсинг. Сейчас мы смотрим на систему как на "черный ящик". 
Когда приходит жалоба о потере заказа, мы не знаем, что случилсь: Упал расчет в MES или потерялось сообщение в RabbitMQ или произошел сбой в CRM. 
На разбор инцидента пирходиться тратить часы на изучение логов с разных сервисов. Это неэффективно.
Трейсинг свяжет все события в одну историю. Мы сможем ввести номер заказа и увидеть его полный путь по системе.

### Предлагаемое решение
В качестве системы распределенного трейсинга предлагается использовать Jaeger со сбором данных по протоколу OpenTelemetry. 
OpenTelemetry является индустриальным стандартом. 
Jaeger хорошо интегрируется с Prometheus/Grafana, которые мы уже планируем внедрить.

Компоненты для внедрения и необходимые доработки:
1. Добавить OpenTelemetry SDK во все бэкенд-контейнеры: Shop API (Java), CRM API (Java), MES API (C#).
2. Внедрить Jaeger 

[Схема с красными связами](jewerly_c4_model_1.png)

Автоматический мониторинг процесса прохождения заказа, полученный из данных трейсинга, и алертинг будет реализован следующим образом:
1. Сбор метрик из трейсов
2. Экспортируем эти метрики в Prometheus.
3. В Prometheus настроим правила алертов, основанные на бизнес-показателях

[Cхема c зелеными связами](jewerly_c4_model_2.png.png)

Я выделю следующие критические точки где заказ может "зависнуть" и где требуется покрытие трейсингом:
1. Shop API - начало жизненного цикла
2. Очереди RabbitMQ - сообщения могут теряться при сбоях и не доходить до потребителя. Критично видеть что сообщение отправлено, получено.
3. MES API - длительный расчет может упасть или завершится с ошибкой
4. CRM API - на завершающих этапах так же может быть сбой

### Данные для трейсинга
Каждый трейс должен однозначно идентифицировать прохождение заказа. Для этого в каждый спан мы должны включать следующие данные:
1. Уникальный идентификатор заказа - как основной ключ
2. Статус заказа - текущий статус 
3. ID сообщения из очереди - путь через RabbitMQ
4. Время начала и окончания операции - для замера блительности этапа
5. Атрибуты ошибки - для случаев если есть причина сбоя

### Компромиссы
Сбор трейсов создает дополнительную нагрузку на сервисы. Для уменьшения влияния можно вклчюить семплирование и собирать только часть данных
Трейсы генерируют большой объем данных, которые надо хранить. нужна стратегия по глубине хранения. Например глубина хранения не более 3-7 дней для 
оперативного поиска проблем 

### Безопасность
Аутентификация и авторизация:
1. Внедрить аутентификацию 
2. Настроить ролевую модель (RBAC):
   Роль "Разработчик" : полный доступ к просмотру трейсов, поиск по идентификатору заказа.
   Роль "Поддержка" : полный доступ к просмотру трейсов, поиск по идентификатору заказа.
   Роль "Администратор" : настройка инструмента
