### Мотивация

Уважаемая команда!

Проблема производительности MES достигла критического уровня. клиенты жалуются на общую скорость выполнения заказов. 
Наш анализ показывает, что корень проблемы в неэффективной работе с данными.
Принято решение внедрить кеширование, которое позволит:
1. Снизить нагрузку на базу данных: 
2. Увеличить скорость отклика для операторов
Кеширование явялеется более простым способом повысить скорость и даст нам время на текущем этапе подготовиться к горизонтальному масштабированию 

### Предлагаемое решение

1. На первом этапе внедрить серверное кеширование на стороне MES API с использованием структур для хранения данных в памяти
2. На втором этапе когда подойдем к горизонтальному машстабированию можно будет присмотерться к внешнему хранилищу, например Redis

В качестве решения я выбираю паттерн кеширования Cache-Aside, пояснение в сравнении с другими:
| Паттерн  | Описание |  Применимость |
| -------- | ---------| --------------|
|Cache-Aside (выбран)|Приложение само управляет кешем: читает из кеша, при промахе читает из БД и заполняет кеш.|Лучше всего подходит для нашего случая|
|Read-Through|Кеш сам запрашивает данные из БД при промахе|Сложнее в реализации, требует, чтобы кеш "знал" о БД|
|Write-Through|Данные пишутся одновременно и в БД, и в кеш|Не подходит|
|Write-Behind (Write-Back)|Данные пишутся сначала в кеш, а затем асинхронно в БД.|Риск потери данных при сбое кеша|
|Refresh-Ahead|Кеш асинхронно обновляет популярные данные до их истечения.|Может быть полезен для популярных фильтров, но сложен в настройке. Может быть реализован позже как расширение |

Стратегия инвалидации кеша
Для MES можно выбрать комбинированную стратегию инвалидации
1. Основная стратегия: Инвалидация по ключу
   При следующем запросе данные будут прочитаны из БД и положены в кеш заново.
   Простота реализации. Не нужно обновлять сложные структуры в кеше.
2. Вспомогательная стратегия: Временная инвалидация
   Если по какой-то причине инвалидация по ключу не сработала, данные все равно обновятся через TTL.
   Защита от разрастания кеша.

Другие стратегии, которые не подходят
| Стратегия  | Причина  | 
| -------- | ---------| 
|Только TTL|Данные могут устаревать между моментом изменения в БД и истечением TTL|
|Обновление кеша при записи|Пытаться обновить все при изменении одного заказа слишком сложно и затратно. Проще удалить кеш и дать ему заполниться заново при чтении.|
|Polling(частый опрос БД) |Это то, что у нас сейчас, что это создает паразитную нагрузку.|
